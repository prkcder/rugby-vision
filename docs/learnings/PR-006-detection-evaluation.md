# PR 006 - Manual Detection Evaluation Across Confidence Thresholds

## What I Built

A repeatable manual evaluation of the pretrained RF-DETR Nano person
detector on 20 frames of `data/raw/rugby.mp4` at confidence thresholds
**0.20, 0.40 and 0.60**. The goal was to learn how to evaluate the model
consistently and see the precision/recall tradeoff, not to improve it.

`src/rugby_vision/evaluation.py` has two modes:

```bash
uv run python -m rugby_vision.evaluation generate    # images + blank review CSV
uv run python -m rugby_vision.evaluation summarize   # validate review, print metrics
```

- **`generate`**
  - Runs RF-DETR Nano on each sampled frame with a separate `predict()`
    call per threshold and keeps only `class_name == "person"`.
  - Saves, under `outputs/evaluation/` (gitignored):
    - 60 annotated images, `frame-NNNN-tXXX.jpg`, with boxes,
      `person 0.87` labels, and a caption strip *below* the frame such as
      `frame 537 | 9.73s | threshold 0.40 | 11 people`.
    - 20 unannotated references, `frame-NNNN-reference.png`, with only a
      frame/timestamp caption below. They are PNG because JPEG is lossy; a
      check against an independent sequential decode confirmed all 20 are
      pixel-identical to the evaluated frames.
  - Writes `data/evaluation/review.csv`. The code fills only
    `frame_index`, `timestamp_seconds`, `threshold` and `detected_count`,
    and leaves `true_positives`, `false_positives`, `false_negatives`,
    `occlusion_level` and `notes` blank for the reviewer.
  - Refuses to overwrite an existing review CSV unless `--force` is passed.
- **`summarize`**
  - Validates the CSV first and refuses to print any metric if something is
    missing or inconsistent. It lists every problem row.
  - Validation rules:
    - TP/FP/FN are whole numbers ≥ 0.
    - `TP + FP == detected_count`.
    - `TP + FN` (the frame's ground truth) is identical across the three
      thresholds.
    - Each frame has one row per threshold.
    - `occlusion_level`, if filled, is `low`, `medium` or `high`.
  - Otherwise it sums TP/FP/FN over all frames per threshold
    (micro-average) and prints precision, recall and F1.

All TP, FP, FN, occlusion and notes values in `review.csv` were entered by
the manual reviewer. None were generated by code.

### Evaluation policy

- Ground truth is any distinct human a reviewer can confidently identify as
  a separate person, even if partly cropped or occluded.
- It includes players, referees/touch judges and sideline spectators,
  because the pretrained model predicts the generic COCO class "person",
  not a rugby-specific "player" class.
- An ambiguous isolated arm, leg or body fragment is not counted unless a
  separate person can be confidently identified.

Manual matching rules:

- Each prediction can count as at most one true positive.
- Each real person can count as at most one true positive.
- One box covering two real people = 1 TP + 1 FN (the box can match only
  one of them).
- Two boxes on one real person = 1 TP + 1 FP (the duplicate is an FP).
- Poor localization alone was **not** scored as an FP if the box still
  corresponded to a unique real person. This is a person-count evaluation,
  not an IoU/mAP evaluation.

`occlusion_level` scale:

- `low`: people mostly separated and clearly visible.
- `medium`: some partial overlap, cropping or occlusion.
- `high`: dense overlap, ruck/maul, or major partial visibility.

### Frame selection

Gameplay was treated as frames **0–1023** (see Problems I Hit). That range
was split into 20 equal segments and the middle frame of each taken,
`int((i + 0.5) × 1024 / 20)`:

```text
25, 76, 128, 179, 230, 281, 332, 384, 435, 486,
537, 588, 640, 691, 742, 793, 844, 896, 947, 998
```

The selection is deterministic; regenerating produced a byte-identical CSV.
Known hard moments were not added to make the sample harder. The fast
camera pan at frames 825–829 from PR 005 is not in the sample; the nearest
sampled frames are 793 and 844.

### Results

Validated `summarize` output from the completed review:

```text
threshold frames   TP   FP   FN precision  recall     F1
     0.20     20  342  109   36     0.758   0.905  0.825
     0.40     20  258    3  120     0.989   0.683  0.808
     0.60     20  169    0  209     1.000   0.447  0.618
```

- **Ground truth:** 378 people in total across the 20 frames (8–27 per
  frame). `TP + FN = 378` at every threshold, as the validation requires.
- **Occlusion ratings:** 12 frames `high` and 8 `medium`; no frame was
  rated `low`.

**Threshold 0.20**
- Highest recall (0.905): only 36 of 378 people were missed.
- Lowest precision (0.758): 109 of 451 boxes were false positives.
- F1 0.825.
- The review found substantial duplicate, clutter and false detections,
  especially in dense scenes. Reviewer notes include:
  - "bag detected as person" and "bags and extra/duplicate detections";
  - "bag, empty-space, and extra/duplicate detections";
  - "touch judge flag detected as person";
  - "many overlapping or duplicate detections" in a maul.

**Threshold 0.40**
- Precision 0.989: only 3 false positives in the whole sample. One note
  records a "bag detected as person" at frame 25.
- Recall 0.683: 120 people were missed.
- F1 0.808.
- This is a different point on the precision/recall tradeoff, not an
  objectively "best" threshold. Its F1 is close to 0.20's, but it trades
  missed people for far fewer false boxes.

**Threshold 0.60**
- No false positives were recorded **in this 20-frame sample**, so
  precision was 1.000. That does not mean the model never produces false
  positives at 0.60; a larger or different sample could contain some.
- Recall fell to 0.447: 209 of 378 people were missed.
- F1 0.618.

## What I Learned

- **The threshold moves precision and recall in opposite directions.**
  - Lowering it exposed more of the difficult people (cropped, distant,
    partially hidden), which raised recall. It also let in substantially
    more false and duplicate detections, which lowered precision.
  - Raising it produced cleaner output with almost no false boxes, but
    missed many more real people.
- **Dense scenes make manual evaluation harder.** Mauls, overlapping
  players, partial visibility and cropping made boxes hard to separate and
  count. Reviewer notes repeatedly say so ("dense maul; overlapping boxes
  difficult to inspect", "overlapping boxes make low-threshold review
  difficult").
- **Merged boxes appear even at high thresholds.** Several frames had one
  box spanning two people, including at 0.60 (frames 230, 384, 742, 844).
  Under the matching rules that is 1 TP + 1 FN, so recall is lost even when
  the box itself is confident.
- **A count-based review needs explicit matching rules.** Without "each box
  and each person can be matched at most once", duplicates and merged
  boxes would be counted inconsistently.
- **Built-in consistency checks catch entry mistakes.** `TP + FP` must
  equal the drawn boxes, and `TP + FN` must be the same at every threshold.
  These checks need no knowledge of the image, so they validate the review
  without the code ever deciding the ground truth.
- **OpenCV random seeking was inaccurate for this video**, so `generate`
  switched to sequential decoding to get the exact evaluation frames.
  - `cv2.CAP_PROP_POS_FRAMES` jumped to a nearby keyframe. The returned
    image exactly matched a *different* frame from a sequential read, up to
    about ±27 frames away. Examples: seek to 80 returned frame 55, seek to
    545 returned 531, seek to 831 returned 839.
  - Seeking to frames 1075 and later failed outright.
- **The end of the clip is a phone screen recording of a YouTube player.**
  - The player's title bar and controls fade in from about frame 1025. The
    top-strip brightness drops sharply at 1025, from about 75 to 63,
    against a gameplay baseline of about 101.
  - The phone control centre covers the frame from 1073.
  - Both are non-game edge cases and were excluded from the sample.

## Important Terms

- **True positive (TP)**: a person box matched to one distinct real person.
- **False positive (FP)**: a person box with no distinct real person of its
  own. Examples: a duplicate box, a bag, a flag, or empty space.
- **False negative (FN)**: a real person with no box of their own,
  including the second person under a box that spans two people.
- **Precision** = TP / (TP + FP): when the model draws a person box, how
  often it is a real person.
- **Recall** = TP / (TP + FN): of the real people, how many the model found.
- **F1**: harmonic mean of precision and recall. It is only high when both
  are high.
- **Micro-average**: sum TP/FP/FN over all frames before dividing, so
  crowded frames count proportionally more.
- **Confidence threshold**: the minimum score a box needs to be kept.
- **IoU / mAP**: the formal detection metrics, which match predicted boxes
  to drawn ground-truth boxes by overlap and average precision over all
  thresholds. They were not used here.

## Problems I Hit

1. **Wrong frames from seeking.** Checking `CAP_PROP_POS_FRAMES` seeks
   against a sequential decode found that 19 of the 20 candidate frames
   were wrong.
2. **The first overlay-boundary estimate was wrong.** The plan assumed
   gameplay ran to frame 1072 (the PR 005 control-centre observation). A
   seek-based check then appeared to show the control centre at 1071, but
   that check was itself affected by the seeking problem. A sequential read
   showed the YouTube player UI from about frame 1025.
3. **The caption covered frame pixels** in the first `generate` run. It hid
   part of a person's box at the bottom of frame 537.
4. **One test expectation was wrong.** I expected the last sampled frame to
   be 997; `int(19.5 × 1024 / 20) = int(998.4) = 998`.
5. **Low-threshold images were hard to review.** At 0.20, dense frames had
   many overlapping boxes, which made it difficult to tell duplicates from
   separate people.

## How I Solved Them

1. `read_frames_sequentially()` decodes from the start and keeps only the
   requested indices.
2. Located the UI with sequential frames and a per-frame brightness check
   of the title-bar strip, then set `GAMEPLAY_LAST_FRAME = 1023`.
3. Moved the caption to a strip added below the image
   (`cv2.copyMakeBorder`), with a test that all original pixels survive.
4. Corrected the test to 998; the code was right.
5. Added an unannotated reference image per frame, so people can be counted
   on the clean frame and then compared with each threshold's boxes.

## What I Would Explain to a Customer

We checked the pretrained person detector by hand on 20 frames of the
rugby clip, at three confidence settings.

The setting controls a tradeoff, not a single right answer:

- **At 0.20** it found about 9 in 10 people, but roughly 1 in 4 boxes was
  wrong: duplicates, bags, a flag, empty space.
- **At 0.40** almost every box was a real person (3 wrong boxes in the
  whole sample), but it found only about 2 in 3 people.
- **At 0.60** we saw no wrong boxes in this sample, but it found fewer than
  half the people.

The right setting depends on what a mistake costs in your application:

- If missing a person is expensive (for example, counting everyone on the
  field, or feeding a tracker that needs as many detections as possible), a
  lower threshold makes sense, and the extra false boxes must be filtered
  or tolerated.
- If a false box is expensive (for example, a highlight or alert that must
  never fire on a bag or a flag), a higher threshold makes sense, accepting
  that more people will be missed.

These numbers come from a small, single-reviewer sample, so they show the
tradeoff on this footage. They are not a guarantee of performance.

## Limitations

- Only 20 frames.
- One short rugby clip.
- Frames are temporally correlated (about 1 s apart, same match and
  camera), so they are not 20 independent samples.
- One manual reviewer; no second reviewer checked agreement.
- Simplified count-based matching.
- No IoU localization scoring: a poorly placed box still counted as a TP if
  it corresponded to a unique person.
- Not COCO mAP, which sweeps all thresholds and several IoU cutoffs on a
  large standard dataset.

Therefore these numbers **cannot be compared directly with published
RF-DETR benchmark results**.
